Day1：从 OrderNoGenerator 到雪花算法 — 分布式ID生成器实战

14天Java面试实战 · 每晚21:30~23:30 · 手写代码深入理解面试题

项目背景

我在学习一个 flight-booking（机票预订系统）项目，它的订单号生成器 OrderNoGenerator 使用了 AtomicLong 来保证线程安全。但面试官追问了一句：

❓ "你们项目部署两台服务器，订单号会重复吗？"

这一问，就引出了今天要攻克的知识点——分布式ID生成器。

原代码的问题

问题分析：

  • AtomicLong 保证的是 JVM 内部的线程安全
  • 但两台服务器有各自的 JVM，SEQUENCE 各自从 0 开始计数
  • 订单号必然重复！

解决方案：雪花算法（Snowflake）

Twitter 开源的雪花算法，用 64 位 long 表示一个唯一ID：

0 | 0000000000 0000000000 0000000000 0000000000 0 | 000000 | 0000 00000000
↑                         ↑                          ↑          ↑
符号位(1)              时间戳(41)                 机器ID(10)   序列号(12)

为什么选它？

方案优点缺点
Auto_increment简单依赖数据库，性能差
UUID不重复无序，太长(36位)，索引性能差
Redis INCR跨JVM依赖Redis可用性
雪花算法 ✅无依赖、高性能、趋势递增依赖系统时钟

手写实现——逐行解析

1️⃣ 常量定义

💡 位运算面试考点：~(-1L << SEQUENCE_BITS) 是什么意思？

  • -1L 的二进制是 1111...1111（64个1）
  • << 12 左移12位，低位补0 → 低12位是0，高位是1
  • ~ 按位取反 → 低12位变成1，高位变成0
  • 结果就是 0000...0000 111111111111 = 4095

这就是位运算求 2^n - 1 的标准写法！

2️⃣ 位移常量——为什么要左移？

💡 左移类比：把三个积木（时间戳、机器ID、序列号）拼成一个64位的long，左移就是给每个积木腾出位置，再用 | 拼接。

3️⃣ 核心算法——nextId()

4️⃣ 位运算溢出原理

sequence = (sequence + 1) & MAX_SEQUENCE;

当 sequence = 4095（二进制 111111111111）时：

4095 + 1 = 4096 = 1 0000 0000 0000 (二进制)
                  &   1111 1111 1111  (MAX_SEQUENCE)
                  ───────────────────
                  =   0000 0000 0000  = 0 ✅ 自动回到0

比 if (sequence > MAX_SEQUENCE) sequence = 0 更优雅，性能更高！

今日面试知识清单

  1. AtomicLong 只保证JVM内线程安全，不跨JVM
  2. 分布式ID方案对比：自增ID vs UUID vs Redis vs 雪花算法
  3. 雪花算法位分配：1符号 + 41时间戳 + 10机器ID + 12序列号 = 64位
  4. 位运算：<< 左移腾位置，& 取模溢出，| 拼接ID
  5. 时钟回拨问题：检测到回拨抛异常，避免ID重复
  6. 自旋等待：序列号用完时循环等待下一毫秒
  7. START_EPOCH 起始时间：减掉起始值让数字变小，可用69年

📕 错题本

知识点: 位运算左移 (<<)
❌ 我最初以为: WORKER_ID_SHIFT 要用 ~(1L << SEQUENCE_BITS)
💡 实际: 左移多少位就是一个简单的数字 12
✅ WORKER_ID_SHIFT = SEQUENCE_BITS;  // 直接赋值
